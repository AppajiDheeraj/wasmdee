## The WASI Contract

wasmdee currently runs **WASI command modules**. Your function is a standard program with a `main()` / `_start` entrypoint:

| Channel | Purpose |
|---|---|
| **stdin** | Receives the request body (from `--data` or HTTP POST body) |
| **stdout** | Your function's response (returned to the caller) |
| **stderr** | Logs and diagnostics (captured but not returned as response) |
| **argv** | Optional arguments (from `--arg` or `?arg=` query params) |
| **exit code** | 0 = success, non-zero = error |

## Supported Languages

Any language that compiles to `wasm32-wasi` works. Here are the tested paths:

### Go (TinyGo)

```go
package main

import (
    "encoding/json"
    "fmt"
    "io"
    "os"
)

func main() {
    input, _ := io.ReadAll(os.Stdin)
    
    var req map[string]string
    json.Unmarshal(input, &req)
    
    fmt.Printf("Hello, %s!", req["name"])
}
```

```bash
tinygo build -o hello.wasm -target wasi .
wasmdee deploy hello.wasm --name hello
```

<Note>
Use TinyGo rather than standard Go for Wasm. Standard Go's WASI support produces larger binaries and has limited compatibility.
</Note>

### Rust

```rust
use std::io::{self, Read, Write};

fn main() {
    let mut input = String::new();
    io::stdin().read_to_string(&mut input).unwrap();
    
    let output = format!("Processed: {}", input.len());
    io::stdout().write_all(output.as_bytes()).unwrap();
}
```

```bash
cargo build --target wasm32-wasi --release
wasmdee deploy target/wasm32-wasi/release/my_func.wasm --name process
```

### Zig

```zig
const std = @import("std");

pub fn main() !void {
    const stdin = std.io.getStdIn().reader();
    const stdout = std.io.getStdOut().writer();
    
    var buf: [4096]u8 = undefined;
    const n = try stdin.read(&buf);
    
    try stdout.print("Got {d} bytes\n", .{n});
}
```

```bash
zig build-exe -target wasm32-wasi src/main.zig
wasmdee deploy main.wasm --name zigfunc
```

### AssemblyScript

```typescript
import { stdin, stdout } from "as-wasi/assembly";

const input = stdin.readString();
stdout.write("Echo: " + input);
```

## Function Capabilities

Each function can declare system access in a `wasmdee.toml` alongside the source:

The current guest surface does not provide networking, KV, or preopened
filesystem directories. The YAML `controls` block configures preload,
concurrency, and scale-to-zero behavior; it is not a capability grant system.

## Reusable Handler ABI

Functions that need the pooled fast path must export:

```text
memory
wasmdee_alloc(i32) -> i32
wasmdee_handle(i32, i32) -> i64
wasmdee_reset() -> i32
```

The handler receives request bytes in linear memory and returns a packed
response pointer and length. A zero reset result declares the borrowed instance
safe for reuse. Failed resets, traps, timeouts, and invalid memory ranges cause
the runtime to discard the instance.

See the runnable `examples/handler` fixture for the complete lifecycle.

## Best Practices

<AccordionGroup>
  <Accordion title="Keep functions small">
    Wasm modules compile faster and instantiate with less memory when they're small. Strip debug symbols and avoid large standard libraries where possible.
  </Accordion>

  <Accordion title="Use stdin/stdout for I/O">
    The current runtime contract is stdin → stdout. Don't rely on filesystem access or network unless you've declared it in capabilities.
  </Accordion>

  <Accordion title="Handle errors via exit code">
    Return exit code 0 for success. Non-zero exit codes are reported as errors to the caller. Write diagnostic information to stderr.
  </Accordion>

  <Accordion title="Reset pooled mutable state">
    WASI command invocations receive fresh instances. Handler modules are reused, so `wasmdee_reset` must restore allocator cursors, buffers, globals, and request-local state before returning zero.
  </Accordion>

  <Accordion title="Test locally before deploying">
    You can run your Wasm module directly with Wasmtime or wasmer for quick iteration before deploying to wasmdee.
  </Accordion>
</AccordionGroup>

## Module Size Guidelines

Smaller modules generally reduce storage, compilation work, and transfer cost,
but language toolchains and imports matter as much as file size. Measure cold,
rehydrate, and warm behavior with `wasmdee bench` before setting a size budget.

Use `wasm-opt` from [Binaryen](https://github.com/WebAssembly/binaryen) to shrink modules:

```bash
wasm-opt -O3 -o optimized.wasm input.wasm
```
