## Overview

wasmdee tracks per-function telemetry for every deployed function. This data feeds future runtime decisions (warm policy, autoscaling, proto-faaslet templates) and is exposed through `GET /runtime`.

---

## Per-Function Metrics

Each function accumulates:

| Metric | Type | Description |
|---|---|---|
| `accepted` | counter | Invocations admitted to the dispatcher |
| `rejected` | counter | Invocations rejected (queue full) |
| `started` | counter | Invocations that began execution |
| `completed` | counter | Invocations that finished (success or failure) |
| `failed` | counter | Invocations that returned a non-zero exit or error |
| `in_flight` | gauge | Currently executing invocations |
| `ewma_latency_ms` | gauge | Exponentially weighted moving average latency |
| `ewma_arrival_rate` | gauge | Exponentially weighted moving average invocations/sec |
| `last_invoked_at` | timestamp | When this function was last called |
| `last_error` | string | Most recent error message (if any) |

---

## EWMA Calculations

Exponentially Weighted Moving Averages smooth out short-term spikes to give a rolling view of function behavior:

- **Latency EWMA** — useful for detecting functions that are becoming slow (memory pressure, cold rehydration)
- **Arrival Rate EWMA** — useful for identifying hot functions that should stay in the warm pool

### GET /healthz

Returns a lightweight subset (engine + dispatcher stats only) suitable for load balancer health checks.

## Why This Matters

Telemetry is the prerequisite for intelligent runtime behavior:

1. **Warm pool policy** — keep frequently-called functions compiled; evict cold ones
2. **Autoscaling signals** — arrival rate drives worker scaling decisions
3. **Proto-faaslet templates** — latency + arrival rate determine which functions deserve a reusable instance template
4. **Debugging** — `last_error` and `failed` counts surface problems without log diving
